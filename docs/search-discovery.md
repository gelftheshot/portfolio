# Search and AI discovery

The portfolio keeps its scrolling homepage and provides a permanent, statically rendered `/projects/[slug]` page for each project. Project descriptions, technical context, references, role labels, and links are ordinary readable content. Employment responsibility details remain in the initial HTML when shown in expandable sections; opening a disclosure does not fetch their text from an API. The expanded pages give both visitors and crawlers a place to inspect the work without opening a JavaScript-only dialog. `/llms-full.txt` also provides the public professional profile, employment detail, all project descriptions, and client feedback in one HTTP response.

The homepage shows three featured projects, three employment entries, and three skill areas. The remainder stays rendered inside native Read more disclosures, so closed sections retain their complete text in the initial HTML.

Client feedback is one horizontally scrollable row. Every review card is server rendered once; the motion wrapper does not clone or conditionally fetch cards. Focus, hover, manual interaction, and offscreen placement pause playback. Reduced-motion preferences start playback paused, and manual controls remain available.

## Canonical site configuration

`lib/site.js` provides `siteUrl`, `absoluteUrl(path)`, `personId`, and the explicit `contentUpdated` date. The default origin is `https://www.lihongebre.com`, the portfolio's adopted custom domain. The shared profile, assistant links, and résumé generator use the same configured origin. Set `NEXT_PUBLIC_SITE_URL` to the final public origin before building a deployment that uses another domain. Only HTTP or HTTPS URLs without embedded credentials are accepted; paths, query strings, and fragments are removed because the setting represents an origin. Rebuild after changing it. Never set the production canonical origin to localhost or a temporary preview host.

The root layout includes the professional title, description, self-referencing homepage canonical, author, Open Graph metadata, Twitter card, and crawl/index directives. Individual project pages supply their own titles, descriptions, canonicals, and project images. `/opengraph-image` produces a 1200 × 630 black-and-white typographic sharing image using `next/og`; it needs no remote fonts or image service.

## Content and discovery files

- `/sitemap.xml` lists the homepage and project detail pages using canonical URLs. Redirect aliases and page fragments are excluded. Its `lastmod` comes from the fixed content update date rather than the time of every request; update that date when the content changes.
- `/robots.txt` allows public content for generic crawlers and explicitly for the documented search and user-request agents `OAI-SearchBot`, `ChatGPT-User`, `Claude-SearchBot`, `Claude-User`, `PerplexityBot`, and `Perplexity-User`. Every explicit group repeats the `/api/` exclusion and the file links to the canonical sitemap. These allow rules document the site's intent; the generic group already allows public pages. No separate GPTBot, ClaudeBot, or other model-training policy is introduced. Robots directives are crawler instructions, not authentication or a way to publish private endpoints. Hosting, CDN, or firewall restrictions can still prevent crawling independently of this file.
- `/llms.txt` is an optional plain-text directory of public professional profiles, employment, client work, and project pages. Near the top it links directly to `/llms-full.txt` for a complete public text response. It repeats supported descriptions rather than adding hidden claims or instructions to AI systems. Neither file is an established ranking factor or a substitute for HTML, links, metadata, and a sitemap.
- `/llms-full.txt` is generated from the shared `profile`, `projects`, and `upwork` records, plus the existing public contact email and résumé links. Featured project overviews separate role scope, the product challenge, engineering context, and evidence; training credentials include their listing source. It includes the summary, skill categories, expertise, automation focus, education, languages, all employment descriptions and responsibility areas, every project's overview and technical sections, all project references, and all completed Upwork job ratings and full feedback. A client display name is included only when the shared public record provides one. The Upwork profile indicators are labeled with the source URL and retrieval date, rather than presented as live statistics. The route selects public fields explicitly from the shared knowledge builder; it omits answer instructions, raw account records, contract identifiers, credentials, financial details, and private contract terms. Project evidence notes remain public context. It is a static, UTF-8 `text/plain` response, so reading the complete professional content requires no JavaScript, disclosure interaction, chat request, or second fetch.
- The homepage JSON-LD describes a `ProfilePage`, its `Person`, a `WebSite`, and an `ItemList` of project write-ups. A case study is a `CreativeWork` authored for the portfolio; that does not declare sole ownership of the underlying commercial product. Project descriptions and roles must agree with the visible pages. No awards, reviews, benchmark results, or certifications are invented for structured data.
- The employment history uses the same six records in the visible homepage, assistant knowledge, `/llms.txt`, `/llms-full.txt`, and the person's dated `hasOccupation` roles. Year-only dates retain the precision supplied by Lihon. Role names include the employer, and occupation descriptions mirror visible engineering scope; they do not infer a current employer, exact employment months, named stacks for unspecified employers, or quantitative results. ALX Africa's existing Python, Django, REST API, and database optimization details are preserved.

Project concept images live in `public/projects/*-cover.png`, including `public/projects/seasure-cover.png` and `public/projects/projuno-cover.png`. These are concept illustrations, not live product screenshots or benchmark evidence. Original interface screenshots remain separate supporting images where available. The generated social card is produced by `app/opengraph-image.jsx` and is not a saved project image. Artwork generation prompts and source notes belong in the project artwork documentation.

## Practical limits and verification

These changes improve accessibility, link discovery, descriptive metadata, and the amount of useful project evidence available in HTML. They do not guarantee indexing, rankings, rich results, automatic reading of the optional text files, or citations in AI answers. Google states that its AI search features use the existing search requirements and do not require special AI text files or schema. Technical terminology is useful when it explains actual work; repeated keyword lists and hidden crawler-only content do not provide that evidence. The public full-text version is another representation of the same professional content available through the portfolio, not a hidden prompt for ranking or assistant behavior.

OpenAI documents `OAI-SearchBot` for search and `ChatGPT-User` for user-requested visits; the latter is not an automatic search crawler, and robots rules may not apply to those visits. Anthropic separately documents `Claude-SearchBot` for search and `Claude-User` for requested access. Perplexity similarly distinguishes `PerplexityBot` from `Perplexity-User` and says the requested fetcher generally ignores robots directives. Public-reading permission is therefore expressed consistently here without treating every agent as an indexer or assuming a robots allow rule forces access.

Before publishing, verify the production domain, project URLs, HTML descriptions and canonicals, JSON-LD, social image, sitemap, robots, and both text responses. A single `/llms-full.txt` response should contain every role and responsibility, all project technical paragraphs and references, all completed job ratings and full feedback, the source retrieval date, provided public client display names, and public contact links. It must not contain assistant system instructions or raw private account fields. After publishing, a verified site owner can use Google Search Console and Bing Webmaster Tools to inspect indexing and submit the sitemap. This local implementation does not submit the site to those services or change their account settings.
